# D-004 · Consumo de las API de Nexora y comportamiento cuando no están disponibles

**Etapa:** E1 · **Estado:** borrador para la puerta «arquitectura»

## Contexto
- **Criterios Datos y Estado:** cada API se consume a través de un repositorio con interfaz definida, sustituible por una implementación simulada cuando la API no existe. Las pantallas no llaman a la API.
- **Estado de las API que necesita esta versión** (inspeccionado en el código del backend, solo lectura):

| Función de Nexora UI | API | Estado |
|---|---|---|
| Tarjetas del diccionario semántico | `Nexora-Semantic`:<br>· `GET/POST /api/v1/data-sources/{id}/definitions`<br>· `GET/PUT …/{definitionId}`<br>· `POST …/approve` y `…/deactivate`<br>· `GET /api/v1/data-sources` | **Existe.** JSON y paginación `page`/`size`. Concurrencia con `ETag`/`If-Match`. Errores *problem+json*. |
| Gestión de reglas | — | **No existe** ningún controlador de «reglas» en Semantic ni en Intelligence (ver Dudas). |
| Chat de pruebas | `Nexora-Intelligence` `POST /api/v1/questions` | Existe, pero **solo responde en *loopback***, **sin autenticación de usuario** (decisión de piloto del backend) y con el inquilino fijado por un alias configurado. Un navegador no puede usarla de forma segura fuera del entorno local. |

- Ninguna API configura CORS.

## Decisión

### Rutas y origen
- La aplicación llama siempre a **rutas relativas del mismo origen**, con un prefijo por API:
  - `/api/semantic/…` → Nexora Semantic
  - `/api/intelligence/…` → Nexora Intelligence
- **En desarrollo:**
  - `proxy.conf.json` del servidor de Angular reenvía `/api/semantic` → `http://localhost:8080` y `/api/intelligence` → `http://localhost:<puerto de Intelligence>`, y quita el prefijo.
  - Así no hace falta CORS en el backend.
- **Fuera de desarrollo:** lo hace un *proxy* inverso del mismo origen. Su configuración es de despliegue y queda fuera de alcance.
- `environment.ts` y `environment.development.ts` tienen esta forma, tipada con una interfaz en `src/environments/environment.model.ts`:
  ```ts
  {
    keycloak: { url, realm: 'nexora', clientId: 'nexora-ui' },
    apis: {
      semantic:     { baseUrl: '/api/semantic' },
      intelligence: { baseUrl: '/api/intelligence' },
    },
    modules: {
      dictionary: { data: 'http' | 'simulated' },
      rules:      { data: 'http' | 'simulated' },
      testChat:   { data: 'http' | 'simulated' },
    },
  }
  ```
  No contiene secretos.

### Repositorio por módulo
1. **Contrato.** `application/<module>.repository.ts` es una clase abstracta. Sus métodos devuelven `Promise<T>` con **modelos del módulo**, nunca DTO ni `HttpResponse`.
   - Las peticiones de esta versión son de una sola respuesta, así que la promesa basta.
   - La fachada guarda el resultado en *signals*.
2. **Implementación real.** `data/http-<module>.repository.ts` usa `HttpClient` y `firstValueFrom`, y convierte DTO → modelo en funciones puras del mismo archivo.
   - Las versiones (`ETag`) se guardan en el modelo como `version` y se envían en `If-Match`.
   - Todo error HTTP se convierte en `NexoraError` con `toNexoraError()` de `shared/data`.
3. **Implementación simulada.** `data/simulated-<module>.repository.ts` trabaja en memoria con datos de ejemplo fijos.
   - Aplica las mismas reglas visibles que la real: validaciones, estados y la regla de que el autor no aprueba su propia tarjeta.
   - Añade un retardo de 300 ms para que se vean los estados de carga.
   - **No persiste nada:** al recargar, vuelve a los datos iniciales.
4. **Elección.** En `<module>.routes.ts`:
   `{ provide: XRepository, useClass: environment.modules.x.data === 'http' ? HttpXRepository : SimulatedXRepository }`.
   Cambiar de simulada a real es cambiar **un valor** en `environment` y recompilar. Ninguna pantalla ni fachada cambia.
5. **Pruebas.** Las pruebas de la fachada usan la implementación simulada. Las del repositorio real usan `HttpTestingController`.

### Errores normalizados
`shared/data/nexora-error.ts` define una unión discriminada:
```ts
type NexoraError =
  | { kind: 'unavailable';  requestId?: string }                    // red caída, timeout, 502/503/504
  | { kind: 'unauthorized' }                                        // 401 (lo trata el interceptor, D-003)
  | { kind: 'forbidden';    requestId?: string }                    // 403
  | { kind: 'not-found';    requestId?: string }                    // 404
  | { kind: 'conflict';     requestId?: string }                    // 409 / 412: alguien cambió el dato antes
  | { kind: 'invalid';      fields: Record<string, string>; requestId?: string } // 400/422 con problem+json
  | { kind: 'unexpected';   requestId?: string };                   // cualquier otro
```
- `requestId` sale de la cabecera `X-Request-Id` cuando el backend la envía.
- La fachada expone el error como *signal* (`error: Signal<NexoraError | null>`). Las pantallas nunca ven `HttpErrorResponse`.
- No hay reintentos automáticos: el reintento lo pide siempre el usuario.

### Qué muestra la interfaz
| Situación | Qué ve el administrador |
|---|---|
| **La API todavía no existe** (módulo con `data: 'simulated'`) | Todas las pantallas del módulo funcionan con los datos simulados. Llevan arriba, fijo y sin opción de cerrarlo, el aviso `simulated-data-notice`, con icono de información: **«Datos de demostración. Esta sección todavía no está conectada a Nexora: los cambios no se guardan.»** La interfaz **nunca** muestra datos simulados sin este aviso. |
| **La API existe pero no responde** (`unavailable`) | En lugar del contenido de la sección aparece `error-state`: **«No se ha podido conectar con Nexora. Inténtalo de nuevo en unos minutos.»**, el botón «Reintentar» y, en letra pequeña, «Referencia: `<requestId>`» si existe. El menú y el resto de secciones siguen funcionando. **Nunca se pasa en silencio a datos simulados.** |
| Falla una acción (guardar, aprobar…) | El formulario conserva lo escrito. Una barra de aviso (`MatSnackBar`) explica el problema, y los errores `invalid` se pintan junto a su campo. Con `conflict`: «Otra persona ha cambiado esta tarjeta. Recárgala para ver la versión actual.», con el botón «Recargar». |
| `forbidden` / `not-found` | «No tienes permiso para hacer esta operación.» / «Este elemento ya no existe.», con el botón para volver a la lista. |
| Lista vacía | `empty-state` con un texto propio del módulo y, si el usuario tiene permiso, la acción de crear. |
| Cargando | `loading-state`: barra de progreso lineal arriba del contenido. No se usan pantallas en blanco. |

Los textos están escritos para un administrador de negocio, sin códigos HTTP ni términos técnicos. Es el mismo principio de comunicación que el backend registra como DEC-COM-1.

### Modo de cada módulo al empezar
| Módulo | `data` en desarrollo | `data` en `environment.ts` |
|---|---|---|
| `dictionary` | `http` | `http` |
| `rules` | `simulated` | `simulated` |
| `testChat` | `simulated`. Puede ponerse en `http` **solo en desarrollo** a través del *proxy* local, porque Intelligence solo atiende *loopback* (ver Dudas). | `simulated` |

## Alternativas descartadas
- **Un servidor de *mocks* aparte (json-server, WireMock) o MSW en el navegador.** Simula a nivel HTTP, así que hay que mantener contratos falsos de una API que en el caso de reglas ni siquiera existe. También añade una dependencia o un proceso más (**Simple**, **Eficiente**). El criterio **Datos** pide sustituir el **repositorio**, y eso es lo que hace esta decisión.
- **Pasar a datos simulados cuando la API real falla.** Mostraría datos falsos como si fueran reales, que es el peor fallo posible en una herramienta de administración. Se descarta sin matices.
- **Activar CORS en el backend y llamar a URL absolutas.** Exige cambiar los repositorios de Nexora, y eso está fuera de alcance. Además, con el mismo origen el *interceptor* de D-003 queda más simple y seguro.
- **Configuración en tiempo de ejecución (`config.json` descargado al arrancar).** Permite usar la misma compilación en varios entornos, pero el despliegue está fuera de alcance y añade una petición y un estado de carga más al arranque. Se puede reconsiderar cuando haya etapa de despliegue.
- **Observables en el contrato del repositorio.** No hay flujos continuos en esta versión. Las promesas con *signals* simplifican las fachadas y sus pruebas.

## Consecuencias
- Cada módulo nuevo trae sus dos implementaciones de repositorio. La simulada es obligatoria mientras su API no exista y se conserva después para las pruebas de la fachada.
- La implementación simulada va dentro del *chunk* del módulo, cargado bajo demanda, y no pesa en la carga inicial.
- Cuando una API pase a existir, se escribe la implementación `http` y se cambia el valor en `environment`. Si el contrato real difiere del modelo provisional, solo cambian `application/*.models.ts` y las pantallas que muestran los campos nuevos.
- No cambia ninguna decisión vigente.

## Dudas para el responsable
1. **¿Qué son las «reglas»?** No existe ninguna API de reglas en Nexora. Recomiendo construir el módulo `rules` con repositorio simulado y este modelo provisional: nombre, descripción en lenguaje de negocio, fuente de datos, estado (borrador / activa / desactivada), autor y fecha. Hay que confirmar si «reglas» se refiere a otra cosa existente, por ejemplo la política de exposición (`/exposure-policy`) o las reglas de aprobación del catálogo. Si es así, cambia el contrato del módulo.
2. **Chat de pruebas contra Intelligence.** `POST /api/v1/questions` no autentica al usuario y solo atiende *loopback*. Recomiendo permitir `http` solo en desarrollo local (vía *proxy*) y `simulated` en cualquier otro entorno, hasta que el backend publique un endpoint con token de usuario. ¿Es aceptable?
