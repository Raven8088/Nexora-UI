# D-001 · Arquitectura, base visual e inventario de API de Nexora UI · etapa E1

## Contexto

Nexora UI no existe todavía: el repositorio solo contiene `.factory/` y `.claude/`. La etapa E1 debe decidir tecnología,
estructura, estado, acceso a API, pruebas y base visual; inventariar la API del backend para las funciones
administrativas previstas (reglas; tarjetas del diccionario semántico: crear, modificar, activar, aprobar; chat de
prueba de peticiones); y dejar un esqueleto que compile, arranque con un comando y pase una prueba.

Respuestas del responsable que fijan el alcance funcional de esta decisión:
- **Reglas** son dos funciones distintas:
  - la **política de exposición** se construye con la API que ya existe;
  - las **reglas de negocio ejecutables** esperan a que el backend tenga API y no se simulan.
- **Activar** una tarjeta cubre las dos lecturas. La interfaz muestra el estado de cada tarjeta y ofrece las acciones
  que el backend ya permite: aprobar, desactivar y recuperar una inactiva. No se pide ningún endpoint nuevo.
- **El chat de prueba de peticiones queda en pausa.** Figura en el inventario como función aplazada, con lo que falta
  en el backend, y queda fuera del plan de pantallas y de la estructura de `funciones/` prevista.
- **`alcance.json`** lo amplía el responsable tras aprobar esta decisión.

Restricciones que condicionan la decisión (de `ficha.md` y `criteria.md`):
- Herramienta solo de administración:
  - navegador de escritorio (Chrome y Edge actuales);
  - menos de 20 usuarios simultáneos;
  - el código lo mantiene una sola persona.
- Capas separadas: pantallas, componentes, lógica de aplicación y acceso a API. Una pantalla nunca llama a la red.
- Un módulo por función, que solo importa de lo compartido. Los límites se comprueban con una regla automática.
- Tipado estático. Cada dato de API tiene una sola definición, derivada del contrato del backend.
- Rendimiento:
  - primera carga en menos de 3 s en red local;
  - el código de cada pantalla se carga bajo demanda;
  - una lista de 5.000 elementos no bloquea la interfaz.
- Escalabilidad: pasar de 3 a 20 pantallas sin reorganizar carpetas; una pantalla nueva no modifica las existentes.
- Seguridad:
  - inicio de sesión con Keycloak;
  - tokens fuera del almacenamiento persistente del navegador;
  - tenant y permisos salen de la sesión verificada;
  - ningún secreto en el código.
- Un único sistema de diseño sin valores sueltos; contraste AA.
- Pruebas unitarias de toda la lógica y al menos una prueba por pantalla.
- Cada dependencia tiene mantenimiento activo, licencia permisiva y justificación.
- No se toca el backend. Si una función no tiene API, su pantalla espera.

Hechos del backend que condicionan el diseño (solo lectura; evidencias en «Inventario de API»):
- Nexora-Semantic expone REST/JSON bajo `/api/v1/...`, protegido con JWT de Keycloak:
  - audiencia `nexora-semantic`; claims `tenant`, `principal_type` y roles;
  - el tenant sale siempre del token, nunca de la petición;
  - concurrencia optimista con ETag e `If-Match` (428 si falta la cabecera, 412 si no coincide);
  - paginación con `page` y `size`;
  - errores RFC 7807 (`application/problem+json`).
- Nexora-Intelligence (solo afecta al chat aplazado):
  - expone `POST /api/v1/report-requests` y `POST /api/v1/questions`, desactivadas por defecto;
  - solo acepta loopback, sin CORS y con control de `Host` y `Origin`.
- No hay especificación OpenAPI en el backend: la búsqueda no da resultados en la documentación de Semantic,
  Intelligence, Reports, `nexora-contracts/` ni `Documentacion/`.
  - Los únicos contratos legibles por máquina son los JSON Schema de `nexora-contracts/` (report-spec, report-plan,
    logical-plan, report-run y report-artifact).
  - Ninguno cubre la política de exposición ni las tarjetas.

## Decisión

### 1. Tecnología

Angular, en su última versión estable con soporte activo en el momento de crear el esqueleto.
- Como mínimo la 21: desde esa versión las aplicaciones nuevas son *zoneless* y usan Vitest por defecto.
- TypeScript en modo `strict`, componentes *standalone* y Angular CDK.
- El productor fija las versiones exactas en `package.json`.

Justificación con los criterios:
- **Capas y límites:** la inyección de dependencias permite que las pantallas reciban servicios de aplicación sin
  conocer la red. `HttpClient` con interceptores centraliza token, errores y ETag en un único punto (`compartido/api`).
- **Carga bajo demanda:** `loadComponent` y `loadChildren` del router de Angular, sin dependencias adicionales.
- **5.000 elementos:** `cdk-virtual-scroll-viewport` de Angular CDK, del mismo mantenedor.
- **Dependencias:** router, HTTP, formularios, pruebas y desplazamiento virtual vienen de un solo proyecto con
  licencia MIT y calendario público de versiones. Hay menos incorporaciones que justificar y menos convenciones que
  inventar para una sola persona.
- **Coherencia con el backend:** Semantic es Spring (DI, capas, pruebas de arquitectura con ArchUnit). El modelo de
  Angular (servicios inyectados, límites comprobados) es análogo.

### 2. Patrón y estructura de carpetas

Patrón: **módulos verticales por función administrativa (*vertical slices*) con capas internas y un núcleo
compartido**. Cada función es una carpeta autocontenida. La única comunicación entre funciones pasa por
`compartido/`.

Funciones previstas en el plan de pantallas:

| Función de la ficha | Carpeta | Estado |
|---|---|---|
| Inicio | `funciones/inicio/` | E1 (página vacía) |
| Reglas · política de exposición | `funciones/exposicion/` | Etapa posterior; API existente |
| Tarjetas del diccionario semántico | `funciones/tarjetas/` | Etapa posterior; API existente |
| Reglas · reglas de negocio ejecutables | `funciones/reglas-negocio/` (no se crea) | Espera API del backend; no se simula |
| Chat de prueba de peticiones | — (no se crea) | Aplazada por el responsable; fuera del plan |

Estructura:

    src/
      index.html
      main.ts
      styles.css                  ← solo importa estilos/tokens.css y estilos/base.css
      estilos/
        tokens.css                ← ÚNICO lugar con valores de color, tipografía, espaciado, radios y sombras
        base.css                  ← reset y estilos de elementos HTML, solo con var(--…)
      environments/
        environment.ts            ← URL de Keycloak, realm y clientId públicos (sin secretos)
      app/
        app.config.ts             ← providers: router, HttpClient + interceptor
        app.routes.ts             ← una entrada perezosa por función
        app.ts                    ← raíz: marco + <router-outlet>
        compartido/
          ui/                     ← componentes base del sistema de diseño (sin red, sin sesión, sin estado global)
          marco/                  ← cabecera, navegación y contenedor de página
          api/                    ← cliente HTTP: interceptor de token, conversión a ApiProblem (RFC 7807), ETag/If-Match
            contratos/            ← tipos de datos de API, incluido el tipo ApiProblem
              semantic/           ← un archivo por recurso: tipos de petición y respuesta
          sesion/                 ← inicio de sesión Keycloak, sesión en memoria, claims (tenant, roles)
        funciones/
          inicio/
            inicio.routes.ts      ← única entrada pública de la función
            pantallas/            ← componentes enrutados (uno por pantalla) + su .spec.ts
          exposicion/             ← (etapa posterior) misma forma que tarjetas
          tarjetas/               ← (etapa posterior)
            tarjetas.routes.ts
            pantallas/            ← componen la pantalla; leen y escriben estado solo a través de aplicacion/
            componentes/          ← presentación propia de la función; solo @Input/@Output y compartido/ui
            aplicacion/           ← servicios con signals: estado, casos de uso, reglas de la pantalla
            api/                  ← funciones que llaman a endpoints concretos usando compartido/api

E1 solo crea `compartido/` (lo mínimo para el marco), `estilos/` y `funciones/inicio/`. Las demás carpetas las crea
la etapa de cada función.

Dónde va cada tipo de código. Todo archivo de `src/` que importe código propio pertenece a una sola fila (lo
comprueba `ubicacion-conocida`, §3), y la columna «Puede importar de `src/`» es la lista completa: lo que no figura
está prohibido. Cada fila es una regla automática del §3 (columna
«Regla»). Las rutas son relativas a `src/app/` salvo que empiecen por `src/`; `<f>` es el nombre de la función.

| Tipo de código | Carpeta | Puede importar de `src/` | Regla |
|---|---|---|---|
| Arranque y raíz | `src/main.ts`, `app.config.ts`, `app.ts` | `app.config.ts`, `app.ts`, `app.routes.ts`, `compartido/api/`, `compartido/sesion/`, `compartido/marco/` | `capa-raiz` |
| Rutas raíz | `app.routes.ts` | solo `funciones/<f>/<f>.routes.ts` | `capa-rutas-raiz` |
| Entrada de una función | `funciones/<f>/<f>.routes.ts` | `pantallas/` y `aplicacion/` de su función | `capa-entrada-funcion` |
| Pantalla (componente enrutado) | `funciones/<f>/pantallas/` | `pantallas/`, `aplicacion/` y `componentes/` de su función; `compartido/ui/`, `compartido/marco/`, `compartido/api/contratos/` | `capa-pantallas` |
| Componente de interfaz de una función | `funciones/<f>/componentes/` | `componentes/` de su función; `compartido/ui/`, `compartido/api/contratos/` | `capa-componentes` |
| Lógica de aplicación y estado | `funciones/<f>/aplicacion/` | `aplicacion/` y `api/` de su función; `compartido/api/contratos/`, `compartido/sesion/` | `capa-aplicacion` |
| Acceso a un endpoint | `funciones/<f>/api/` | `api/` de su función; `compartido/api/` (incluidos contratos) | `capa-api-funcion` |
| Componente base reutilizable | `compartido/ui/` | `compartido/ui/` | `capa-ui` |
| Marco (cabecera, navegación, contenedor) | `compartido/marco/` | `compartido/marco/`, `compartido/ui/`, `compartido/sesion/` | `capa-marco` |
| Cliente HTTP (interceptor, ApiProblem, ETag) | `compartido/api/` salvo `contratos/` | `compartido/api/` (incluidos contratos), `compartido/sesion/` | `capa-cliente-api` |
| Tipos de datos de API | `compartido/api/contratos/` | `compartido/api/contratos/` | `capa-contratos` |
| Sesión y permisos | `compartido/sesion/` | `compartido/sesion/`, `src/environments/` | `capa-sesion` |
| Configuración pública | `src/environments/` | nada | `capa-environments` |

Paquetes de `node_modules` con uso limitado (los demás, como `@angular/core`, `@angular/router`, `@angular/cdk` o
`rxjs`, no se limitan por capa):

| Paquete | Solo desde | Regla |
|---|---|---|
| `@angular/common/http` | `compartido/api/`, `funciones/<f>/api/`, `app.config.ts` (registra `provideHttpClient` con el interceptor) y archivos `.spec.ts` | `http-solo-en-api` |
| `keycloak-js` | `compartido/sesion/` | `keycloak-solo-en-sesion` |

Notas de la tabla:
- Los archivos `.spec.ts` siguen la fila de su carpeta. Solo quedan exentos de `http-solo-en-api`, para usar
  `HttpTestingController`.
- Pantallas y componentes pueden importar `compartido/api/contratos/` porque son solo tipos: muestran los datos de
  API sin redefinirlos (una sola definición) y sin acceso a la red.
- El tipo `ApiProblem` es un tipo de dato de API y se declara en `compartido/api/contratos/`. `compartido/api` aporta
  la conversión desde `application/problem+json`. Así `aplicacion/` y las pantallas pueden tratar el error sin
  importar el cliente HTTP.
- El marco puede leer la sesión para mostrar el usuario, cerrar sesión y mostrar u ocultar entradas de navegación
  según los roles. Las pantallas no: reciben esa información de `aplicacion/`.
- El interceptor de `compartido/api` lee el token de `compartido/sesion`; la sesión nunca importa el cliente HTTP.

Escalabilidad:
- Una pantalla nueva es una carpeta nueva, más una línea en `app.routes.ts` y una entrada en la navegación de
  `compartido/marco`. Ninguna pantalla existente cambia.
- De 3 a 20 pantallas solo se añaden carpetas en `funciones/`.
- `app.routes.ts` solo referencia funciones mediante `import()` dinámico de su `<f>.routes.ts`.

### 3. Regla automática de límites

dependency-cruiser, configurado en `.dependency-cruiser.cjs` con severidad `error` y ejecutado en
`npm run verificar`. Todas las reglas son `forbidden` y comparan `from` y `to` sobre rutas resueltas. Las tablas
«Dónde va cada tipo de código» del §2 son su especificación: cada fila es una regla con el mismo nombre.

1. **Una regla por fila de la tabla de capas** (las 13 reglas `capa-*`), todas con la misma forma:
   - `from.path`: la carpeta o archivos de la fila. En las filas de `funciones/`, el nombre de la función se
     captura con `([^/]+)`.
   - `to.path`: `^src/`. La regla solo limita las importaciones de código propio; los paquetes de `node_modules`
     solo los limitan las reglas 3 y 4.
   - `to.pathNot`: la columna «Puede importar de `src/`», una expresión por destino. «De su función» se escribe con
     `$1`. En `capa-environments` no hay `pathNot`: cualquier importación de `src/` falla.
   - `capa-cliente-api` lleva además `from.pathNot: ^src/app/compartido/api/contratos/`, porque esa carpeta tiene
     su propia fila.

   Ejemplo, `capa-pantallas`:
   - `from.path`: `^src/app/funciones/([^/]+)/pantallas/`;
   - `to.path`: `^src/`;
   - `to.pathNot`: `^src/app/funciones/$1/(pantallas|aplicacion|componentes)/` y
     `^src/app/compartido/(ui|marco|api/contratos)/`.

   Ejemplo, `capa-rutas-raiz`:
   - `from.path`: `^src/app/app\.routes\.ts$`;
   - `to.path`: `^src/`;
   - `to.pathNot`: `^src/app/funciones/[^/]+/[^/]+\.routes\.ts$`.

   Como `to.path` es `^src/`, la regla no afecta a `@angular/router` ni a ningún otro paquete que `app.routes.ts`
   necesite.
2. `ubicacion-conocida`: desde cualquier archivo de `^src/` cuya ruta no coincida con ningún `from.path` de las
   reglas `capa-*` se prohíbe importar `^src/`. Un archivo fuera de las carpetas previstas no puede usar código
   propio. Además, ninguna fila admite importarlo, así que tampoco puede usarlo nadie.
3. `http-solo-en-api`: se prohíbe `node_modules/@angular/common/.*http` desde cualquier archivo, salvo
   `^src/app/compartido/api/`, `^src/app/funciones/[^/]+/api/`, `^src/app/app\.config\.ts$` y `\.spec\.ts$`.
4. `keycloak-solo-en-sesion`: se prohíbe `node_modules/keycloak-js/` desde cualquier archivo, salvo
   `^src/app/compartido/sesion/`.
5. `sin-ciclos`: `circular: true` está prohibido.

En la entrega, el productor demuestra que cada regla falla (las 13 `capa-*` y las reglas 2 a 5): introduce
temporalmente una violación y después la retira.

### 4. Tipos de datos de la API (una sola definición)

- Cada recurso tiene un único archivo en `compartido/api/contratos/<servicio>/<recurso>.ts` con sus tipos de petición
  y respuesta. Las funciones los importan; nadie redefine un tipo de API.
- Origen del tipo:
  - **Generado**, si el dato tiene JSON Schema en `nexora-contracts/`. Se genera con `json-schema-to-typescript` en
    `contratos/generado/`, no se edita a mano, y la dependencia se incorpora en la etapa que la necesite.
  - **Transcrito** del DTO Java en los demás casos (política de exposición, definiciones, relaciones, sugerencias).
    La cabecera del archivo cita la ruta del controlador y el nombre del record, p. ej.
    `Nexora-Semantic/.../api/catalog/DefinitionController.java` · `DefinitionDtos.DefinitionResponse`.
- Los enumerados del backend (`DefinitionStatus`, `DefinitionKind`…) se declaran como uniones de literales de texto.
- No se generan tipos desde OpenAPI: el backend no lo publica y no se modifica (ver «Dudas para el responsable»).

### 5. Estado y acceso a la API

**Estado:**
- El estado de cada pantalla vive en servicios de `aplicacion/` con `signal`, `computed` y métodos de caso de uso.
  Se proporcionan en los `providers` de la ruta de su función.
- El único estado global es el de la sesión (`compartido/sesion`). Sin NgRx ni almacén global.

**Acceso a la API:**
- `funciones/<f>/api/` usa `HttpClient`.
- `compartido/api` aporta:
  - un interceptor que añade `Authorization: Bearer` solo a las URL que empiezan por `/api/` y renueva el token si
    caduca en menos de 30 s;
  - la conversión de `application/problem+json` a un tipo `ApiProblem` (status, code, detail, errors);
  - utilidades de ETag: lectura de la cabecera `ETag` y envío de `If-Match`.

**URL:**
- El navegador llama siempre a rutas del mismo origen.
- En desarrollo, `proxy.conf.json` (configurado en `angular.json`) reenvía `/api/semantic/` a Nexora-Semantic
  (`http://localhost:8080`) quitando el prefijo.
- Ninguna URL del backend se escribe en el código.
- No se configura ninguna ruta hacia Intelligence mientras el chat esté aplazado.

**Tenant y permisos:**
- El tenant nunca se envía: el backend lo toma del token.
- La interfaz usa los claims solo para mostrar u ocultar acciones; quien autoriza es el backend.

### 6. Tarjetas: estado y acciones (para la etapa de tarjetas)

- Cada tarjeta (definición o relación) muestra su estado del backend con una EtiquetaEstado: DRAFT, APPROVED o
  INACTIVE, y además `usable` cuando la respuesta lo incluya.
- Acciones ofrecidas, todas con endpoints existentes (ver «Inventario de API»):
  - **crear:** `POST` (`semantic:proposal:write`);
  - **modificar:** `PUT` con `If-Match` (`semantic:proposal:write`); la tarjeta vuelve a DRAFT;
  - **aprobar:** `POST …/approve` con `If-Match`. Exige un principal HUMAN con `semantic:proposal:approve`. Desde
    D-DIC-15 el autor o el último editor pueden aprobar su propia tarjeta;
  - **desactivar:** `POST …/deactivate` con motivo y `If-Match`. Exige lo mismo que aprobar: principal HUMAN con
    `semantic:proposal:approve`;
  - **recuperar una inactiva:** `PUT` con `If-Match` (la deja en DRAFT) y después `POST …/approve`. Los dos pasos
    los puede dar la misma persona si tiene `semantic:proposal:write` y `semantic:proposal:approve`.
- La interfaz no oculta que «recuperar» son dos pasos: tras el `PUT`, la tarjeta queda en DRAFT a la espera de
  aprobación.
- La interfaz no impone a las tarjetas ninguna separación entre autor y aprobador: el backend no la exige en el
  catálogo. La regla de dos personas solo se aplica a la política de exposición (D3).
- Ninguna acción usa un endpoint inexistente. Cuando el backend rechaza una acción, la interfaz muestra el
  `ApiProblem` devuelto: permiso, tipo de principal (solo HUMAN aprueba o desactiva) o versión.

### 7. Rendimiento

- Cada función se carga con `loadChildren`/`loadComponent`. El paquete inicial contiene solo la raíz, el marco, la
  sesión y `compartido/api`.
- Presupuestos en `angular.json` (`budgets`): tipo `initial` con aviso a 400 kB y error a 600 kB;
  `anyComponentStyle` con error a 8 kB. `ng build` falla si se superan.
- Medición de los 3 s en la entrega, con Chrome DevTools:
  - red sin limitación y caché desactivada;
  - el resultado de `ng build` servido en la red local;
  - se registra la cifra de *Load*.
- Listas grandes:
  - la capa `aplicacion` reúne todas las páginas del endpoint en memoria;
  - el filtrado es un `computed` sobre un signal con el texto del filtro;
  - la lista se presenta con `cdk-virtual-scroll-viewport`, con la altura de fila fija definida en los tokens y
    filas en CSS grid con roles ARIA de tabla;
  - sin Web Workers: filtrar 5.000 objetos en memoria es una operación de milisegundos.

### 8. Keycloak y seguridad

- `keycloak-js` (proyecto Keycloak, Apache-2.0) vive en `compartido/sesion`.
  - Se inicia con `init({ onLoad: 'login-required', pkceMethod: 'S256', checkLoginIframe: false })`.
  - Usa un cliente **público** (sin secreto) con el flujo Authorization Code + PKCE.
- Los tokens solo viven en la memoria de la instancia de Keycloak.
  - Nunca se escriben en `localStorage`, `sessionStorage`, IndexedDB ni cookies propias.
  - Al recargar la página se repite el redireccionamiento a Keycloak; la sesión SSO de Keycloak lo hace
    transparente.
- Tenant y permisos se leen de los claims del token emitido por Keycloak: `tenant`, `realm_access.roles` y
  `principal_type`. Nunca de un campo, un parámetro de URL ni un almacenamiento editable por el usuario.
- `environment.ts` contiene solo valores públicos (URL de Keycloak, realm y clientId). El repositorio no contiene
  ningún secreto.
- El inicio de sesión se implementa en la primera etapa que consuma una API. E1 entrega una página de inicio vacía
  sin inicio de sesión, como pide la ficha.

### 9. Sistema de diseño

**Tokens.** `src/estilos/tokens.css` define todos los valores como propiedades personalizadas en `:root`:
- **Color:** los tokens de la **Paleta 1 · Blanco + vino tinto**, que el responsable eligió como paleta del
  proyecto (valores y contrastes en «Paletas»).
- **Tipografía:**
  - familias: `--fuente-base: "Segoe UI", system-ui, sans-serif` y
    `--fuente-mono: "Cascadia Mono", Consolas, monospace`;
  - tamaños: `--texto-xs` 12px, `--texto-sm` 14px (base), `--texto-md` 16px, `--texto-lg` 20px, `--texto-xl` 24px y
    `--texto-xxl` 32px;
  - pesos: `--peso-normal` 400 y `--peso-fuerte` 600;
  - `--interlineado` 1.5.
- **Espaciado (base 4px):** `--esp-1` 4px, `--esp-2` 8px, `--esp-3` 12px, `--esp-4` 16px, `--esp-5` 24px,
  `--esp-6` 32px y `--esp-7` 48px.
- **Otros:**
  - radios `--radio-1` 4px y `--radio-2` 8px, y sombra `--sombra-1`;
  - altura de fila de lista `--fila-alto` 40px;
  - anillo de foco: `--foco-ancho` 2px y `--foco-separacion` 2px.

Se usan fuentes del sistema: sin descarga, sin dependencia y sin coste en la primera carga.

**Componentes base.** Viven en `compartido/ui/`, y cada uno se crea en la primera etapa que lo necesite:
- Botón (primario, secundario y peligro), CampoTexto, Selector y Casilla.
- EtiquetaEstado: texto y borde del color de estado, sobre fondo o superficie.
- Aviso (éxito, aviso y error).
- Diálogo (CDK Dialog) y ListaVirtual (CDK).
- CabeceraPágina, IndicadorCarga y EstadoVacío.

E1 crea `tokens.css`, `base.css` y el marco.

**Ningún valor suelto, comprobado automáticamente:**
- stylelint con `stylelint-declaration-strict-value` se aplica a todos los `.css` salvo `tokens.css`.
  - Propiedades comprobadas: `color`, `background-color`, `border-color`, `outline-color`, `fill`, `stroke`,
    `font-size`, `font-family`, `font-weight`, `margin*`, `padding*`, `gap`, `border-radius` y `box-shadow`.
  - Valores admitidos: `var(--…)`, `0`, `auto`, `none`, `inherit`, `transparent` y `currentColor`.
- Los componentes usan siempre `styleUrl` (un archivo `.css`). Una prueba de Vitest recorre `src/app/**` y falla si
  encuentra `styles:`, `style="` o `[style` en plantillas o componentes.

### 10. Pruebas y comandos

**Pruebas:**

## Alternativas descartadas

- **React + Vite + TypeScript.**
  - React solo resuelve la vista. Enrutado, carga de datos, desplazamiento virtual y pruebas de componentes exigen
    elegir e incorporar al menos cuatro paquetes de mantenedores distintos (p. ej. react-router, TanStack Query,
    TanStack Virtual y Testing Library).
  - Además habría que fijar por convención propia dónde vive cada cosa.
  - Choca con «cada dependencia se justifica» y con que una sola persona mantenga la arquitectura.
- **Vue 3 + Vite + TypeScript.**
  - Es más ligero que Angular, pero el tipado de plantillas necesita una herramienta aparte (`vue-tsc`).
  - El desplazamiento virtual depende de bibliotecas de terceros con mantenimiento menos constante.
  - Deja abiertas las mismas decisiones estructurales que React.
- **Angular Material como sistema de diseño.**
  - Su tema M3 deriva paletas tonales de un color semilla. Garantizar exactamente los pares AA de «Paletas» obliga a
    sobrescribir muchas variables del sistema.
  - Añade peso a la primera carga.
  - Los componentes propios sobre CDK dan control directo de los tokens.
- **ESLint + `eslint-plugin-boundaries` para los límites.** Requiere ESLint, `typescript-eslint` y `angular-eslint`
  además del plugin: cuatro paquetes frente a uno (dependency-cruiser) para la misma comprobación.
- **Límites como lista de prohibiciones caso a caso** (la versión anterior del §3, ampliada con las que faltaban).
  Solo cubre los casos que alguien previó, y la tabla y las reglas vuelven a divergir cada vez que cambia una fila.
  Con una regla por fila cuyo `pathNot` es la columna «Puede importar», lo no listado falla por construcción.
- **Sección `allowed` de dependency-cruiser (lista blanca global).** Obliga a listar en cada regla también los
  paquetes de `node_modules` que cada capa usa (`@angular/core`, `router`, `cdk`, `rxjs`…). Además, la violación se
  informa como `not-in-allowed`, sin el nombre de la fila incumplida.
- **NgRx (Store o SignalStore).** Añade una dependencia y un modelo de acciones para un estado local por pantalla con
  menos de 20 usuarios. Los signals nativos bastan.
- **Paleta 2 · Blanco + azul.** Cumple AA en todos los pares (ver «Paletas»), igual que la Paleta 1. La descarta el
  responsable al elegir la Paleta 1 (blanco y vino tinto) como paleta del proyecto.
- **Generar tipos desde OpenAPI.** El backend no publica OpenAPI y no se puede modificar.
- **Guardar tokens en `sessionStorage` o `localStorage`.** Prohibido por las restricciones.
- **Backend-for-Frontend que guarde los tokens en servidor.** Es más robusto frente a XSS, pero añade un servidor que
  mantener y desplegar. Los tokens en memoria cumplen la restricción con menos piezas.
- **Simular las reglas de negocio ejecutables o el chat mientras faltan su API o su autorización.** Prohibido por la
  decisión vigente «no se simula ni se inventa» y por las respuestas del responsable.

## Consecuencias

**Qué facilita:**
- Añadir funciones (incluidas las reglas de negocio y el chat cuando proceda) sin tocar las existentes.
- Comprobar límites y estilos en `npm run verificar`.
- Una primera carga pequeña, con un presupuesto que hace fallar la compilación si se supera.

**Qué complica:**
- **Tipos transcritos.** Los tipos de la política de exposición y de las tarjetas son transcripciones trazables del
  DTO Java, no generados. Si el backend cambia un DTO, hay que actualizar el archivo a mano.
- **Recargas.** Cada recarga de página repite el redireccionamiento a Keycloak, porque no hay tokens persistidos.
- **Estado del redireccionamiento.** keycloak-js guarda durante el redireccionamiento el estado de la llamada de
  vuelta (state, nonce y verificador PKCE; no tokens) y lo borra al volver.
- **Recuperar una tarjeta inactiva** son dos pasos: edición y aprobación. Desde D-DIC-15 los puede dar la misma
  persona. Dos textos de Nexora-Semantic aún describen dos personas para el catálogo: `docs/ARCHITECTURE.md`
  (l. 949) y el javadoc de `DefinitionController.java` (l. 40-41). Están desfasados frente al código, y por eso el
  inventario cita el código.

**Funciones en espera:**
- Las reglas de negocio ejecutables quedan en espera de API y no tienen carpeta hasta entonces.
- El chat queda aplazado. Su reanudación exigirá decidir cómo accede el navegador a Intelligence (ver «Dudas para el
  responsable»).

**Datos y forma de este documento:**
- `alcance.json` de E1 solo permite hoy `docs/**` y `README.md`. El responsable lo amplía tras aprobar esta decisión.
  - El esqueleto necesitará `src/**`, `public/**`, `package.json`, `package-lock.json`, `angular.json`,
    `tsconfig*.json`, `proxy.conf.json`, `.dependency-cruiser.cjs`, `.stylelintrc.json` y `.gitignore`.
- Este archivo reúne varias decisiones (arquitectura, inventario y paletas) por indicación expresa del responsable,
  aunque la norma del arquitecto es un archivo por decisión.
- No cambia ninguna decisión vigente de la ficha.

   pedirá OpenAPI al backend en alguna etapa?
5. **Elección de paleta. Resuelta:** el responsable eligió la Paleta 1 (blanco y vino tinto). Queda fijada en §9 y

7. **Inicio de sesión** (menor): se implementa en la primera etapa que consuma una API, no en E1. ¿Es aceptable?
8. **Estado temporal de keycloak-js** (menor): durante el redireccionamiento guarda el estado de la llamada de vuelta
   (state, nonce y verificador PKCE; no tokens) y lo borra al volver. ¿Es aceptable?
